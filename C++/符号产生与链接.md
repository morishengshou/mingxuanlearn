# 用一个小例子，把「符号产生 → 链接找到」全过程走一遍

> 环境假设：**Linux x86-64 + g++**（Ubuntu/WSL/Docker 都行）。
> macOS / Windows 的差异我在最后单独说。
> 你的编译器版本不同，`nm` 输出的细节可能略有差异，但**原理完全一样**。

---

## 0. 先建好这个小项目

```bash
mkdir symdemo && cd symdemo
```

### 📄 `math_utils.h`

```cpp
#pragma once

namespace mu {

// ---- 只声明，定义在 math_utils.cpp 里 ----
int    add(int a, int b);              // 重载 1
double add(double a, double b);        // 重载 2

extern int g_callCount;                // 【声明】全局变量，定义在 .cpp

class Counter {
public:
    Counter();
    ~Counter();
    void bump();
    int  value() const;
private:
    int n_;
};

// ---- 定义直接写在头文件里 ----
inline int twice(int x) { return x + x; }            // inline 函数

template <class T>
T maxOf(T a, T b) { return (a < b) ? b : a; }        // 模板

} // namespace mu
```

### 📄 `math_utils.cpp`

```cpp
#include "math_utils.h"
#include <cstdio>

namespace mu {

int g_callCount = 0;                   // 【定义】

static int s_secret = 42;              // static：只在本文件可见
static void logCall(const char* who) { // static 函数
    ++g_callCount;
    std::printf("[log] %s  (secret=%d)\n", who, s_secret);
}

int add(int a, int b) {
    logCall("add(int,int)");
    return a + b;
}

double add(double a, double b) {
    logCall("add(double,double)");
    return a + b;
}

Counter::Counter() : n_(0) {}
Counter::~Counter() {}
void Counter::bump()      { ++n_; }
int  Counter::value() const { return n_; }

int helperUsingHeader() {              // 让 twice/maxOf 在本文件也被用到
    return twice(3) + maxOf(1, 2);
}

} // namespace mu
```

### 📄 `main.cpp`

```cpp
#include "math_utils.h"
#include <cstdio>

int main() {
    std::printf("add(1,2)       = %d\n",  mu::add(1, 2));
    std::printf("add(1.5,2.5)   = %f\n",  mu::add(1.5, 2.5));

    mu::Counter c;
    c.bump();
    c.bump();

    std::printf("counter        = %d\n", c.value());
    std::printf("twice(10)      = %d\n", mu::twice(10));
    std::printf("maxOf(3,7)     = %d\n", mu::maxOf(3, 7));
    std::printf("g_callCount    = %d\n", mu::g_callCount);
    return 0;
}
```

## 1. 先建立全局认识：`g++ a.cpp` 背后是 4 个阶段

```
 main.cpp                                                   
    │                                                        
    │ ① 预处理 (cpp)        g++ -E main.cpp -o main.i        
    ▼   展开 #include / 宏，去注释                            
 main.i   ← 纯 C++ 文本，已经没有 #include 了                 
    │                                                        
    │ ② 编译 (cc1plus)      g++ -S main.i -o main.s          
    ▼   语法/语义分析、生成汇编、★★在这里给函数变量"取名字"★★  
 main.s   ← 汇编文本，里面已经出现 _ZN2mu3addEii 这种符号      
    │                                                        
    │ ③ 汇编 (as)           g++ -c main.s -o main.o          
    ▼   文本汇编 → 二进制目标文件 + 符号表 + 重定位表          
 main.o   ← ELF 目标文件（还不能运行！地址都是 0 占位）         
    │                                                        
    │ ④ 链接 (ld)           g++ main.o math_utils.o -o app   
    ▼   ★★合并段 + 分配地址 + 回填符号★★                     
  app     ← 可执行文件
```

**关键一句话：**
> **②③ 阶段负责「产生符号」（一个 .cpp 只管自己，不知道别人）；
> ④ 阶段负责「匹配符号」（把 `U` 未定义 的和 `T` 已定义 的配对）。**

`.cpp` 之间**唯一的通信方式就是符号名字符串**。这就是为什么名字必须编码进类型信息（mangling）。

### 2.3 逐个解释这些符号是怎么"拼"出来的

| 源码 | 符号 | 拆解 |
|---|---|---|
| `mu::add(int,int)` | `_ZN2mu3addEii` | `_Z`开头 `N`嵌套开始 `2mu`(长度2+名字) `3add` `E`嵌套结束 `i`=int `i`=int |
| `mu::add(double,double)` | `_ZN2mu3addEdd` | 同上，`d`=double → **重载能共存的原因** |
| `mu::g_callCount` | `_ZN2mu11g_callCountE` | 变量没有参数列表，`E` 之后就结束了 |
| `mu::Counter::Counter()` | `_ZN2mu7CounterC1Ev` | `C1`=构造函数，`v`=void 参数 |
| `mu::Counter::~Counter()` | `_ZN2mu7CounterD1Ev` | `D1`=析构函数 |
| `mu::Counter::value() const` | `_ZNK2mu7Counter5valueEv` | `N`后面的 `K` = **const 成员函数** |
| `mu::logCall`（static） | `_ZN2muL7logCallEPKc` | `L` = 内部链接（static）；`PKc` = `const char*`（从右往左读：c=char，K=const，P=指针）|
| `mu::maxOf<int>` | `_ZN2mu5maxOfIiEET_S1_S1_` | `I..E`=模板参数`<int>`；`T_`=第0个模板参数；`S1_`=前面出现过的类型的"压缩引用" |
| `std::printf` | `printf` | C 标准库函数是 `extern "C"`，**不 mangle** |

> 🔑 **记住这条**：`nm -C` 和 `c++filt` 就是你的翻译器，规则不用背。

### 2.4 符号类型字母（最重要的 4 个）

| 字母 | 含义 | 本例 |
|---|---|---|
| `T` | **T**ext，全局函数（其他 .o 能看到） | `mu::add` |
| `t` | 小写 = **static**，只有本文件能用 | `mu::logCall` |
| `U` | **U**ndefined，我需要，别人提供 | `main.o` 里的 `mu::add` |
| `B`/`b` | .bss，未初始化/零初始化的全局变量 | `mu::g_callCount = 0` |
| `D`/`d` | .data，有非零初值的全局变量 | `mu::s_secret = 42` |
| `W` | **W**eak，弱符号（inline/模板/`template` 实例） | `mu::twice` |

## 3. .o 里的另一半：**重定位表**（链接器的"待办清单"）

符号表说"我需要 `_ZN2mu3addEii`"，但**具体需要填在哪个字节位置**？这由重定位表记录。

```bash
objdump -dr -C main.o | head -40
```

```asm
0000000000000000 <main>:
   0:   f3 0f 1e fa             endbr64
   4:   55                      push   %rbp
   5:   48 89 e5                mov    %rsp,%rbp
   ...
  0e:   be 02 00 00 00          mov    $0x2,%esi
  13:   bf 01 00 00 00          mov    $0x1,%edi
  18:   e8 00 00 00 00          call   1d <main+0x1d>        ← ★★★
                        19: R_X86_64_PLT32   mu::add(int, int)-0x4
  1d:   89 c6                   mov    %eax,%esi
  ...
```

看这一行：

```
  18:   e8 00 00 00 00          call
        ↑  ↑  └──────┬──────┘
        │  │         └── 4 字节的目标地址：全是 0 ！！这是【占位符】
        │  └── e8 = x86 的 "call 相对地址" 指令
        └── 这条指令在 .text 段里的偏移
```

下面紧跟的一行就是**重定位记录**：

```
19: R_X86_64_PLT32   mu::add(int, int) - 0x4
↑        ↑                    ↑
│        │                    └─ 要填谁的地址
│        └─ 怎么算（32位相对偏移，PLT 方式）
└─ 从第 0x19 字节开始填（跳过 e8 这 1 字节）
```

**可视化：**

```
        main.o 的 .text 段
   ┌────────────────────────────────────────┐
   │ ...                                    │
   │ 0x18: e8 [00 00 00 00]  ← 空洞①        │
   │ 0x2b: e8 [00 00 00 00]  ← 空洞②        │
   │ ...                                    │
   └────────────────────────────────────────┘
            ▲            ▲
            │            │
   ┌────────┴────────────┴───────────────────┐
   │ 重定位表 (.rela.text) —— 待办清单        │
   │  偏移 0x19 → 填 _ZN2mu3addEii 的地址     │
   │  偏移 0x2c → 填 _ZN2mu3addEdd 的地址     │
   │  偏移 ...  → 填 _ZN2mu7CounterC1Ev ...   │
   └─────────────────────────────────────────┘
   
   ┌─────────────────────────────────────────┐
   │ 符号表 (.symtab)                        │
   │  main              定义在本文件 0x0      │
   │  _ZN2mu3addEii     U （不知道在哪！）     │
   │  printf            U                    │
   └─────────────────────────────────────────┘
```

> 一个 `.o` = **代码/数据** + **符号表（我有什么、我缺什么）** + **重定位表（缺的东西要填在哪）**

### ❌ 错误 2：声明和定义的签名不一致（新手最常踩）

在 `math_utils.h` 加一行声明：

```cpp
int sub(int a, int b);        // 声明：int, int
```

在 `math_utils.cpp` 里定义时手滑写成 `long`：

```cpp
int sub(long a, long b) { return a - b; }   // 定义：long, long ← 不一样！
```

`main.cpp` 里调用 `mu::sub(5, 3)`，结果：

```
undefined reference to `mu::sub(int, int)'
```

**"我明明写了啊！"** —— 用符号表一秒看穿：

```bash
nm -C math_utils.o --defined-only | grep sub
# 0000000000000120 T mu::sub(long, long)      ← 提供的是这个

nm -C main.o -u | grep sub
#                  U mu::sub(int, int)        ← 需要的是这个
```

看原始名字更直观：

```
_ZN2mu3subEll   ≠   _ZN2mu3subEii
```

> **对编译器来说这是两个完全不相干的名字。**
> 同类陷阱：忘写 `const`（`_ZNK...` vs `_ZN...`）、`&` vs 值传递、命名空间写错。

### ❌ 错误 3：C 和 C++ 混用，忘了 `extern "C"`

建 `legacy.c`：

```c
/* legacy.c —— 用 C 编译器编译 */
int c_add(int a, int b) { return a + b; }
```

`main.cpp` 里直接声明使用：

```cpp
int c_add(int, int);      // ← 没有 extern "C"
int main() { return c_add(1, 2); }
```

```bash
gcc -c legacy.c -o legacy.o
g++ -c main.cpp -o main.o
g++ main.o legacy.o -o app
# undefined reference to `c_add(int, int)'
```

**看符号：**

```bash
nm legacy.o --defined-only | grep c_add
# 0000000000000000 T c_add            ← C 编译器：不 mangle

nm main.o -u | grep c_add
#                  U _Z5c_addii       ← C++ 编译器：mangle 了！
```

**修复：**

```cpp
extern "C" int c_add(int, int);       // 告诉 C++ 编译器"别 mangle"
// 或者整块：
// extern "C" { #include "legacy.h" }
```

改后：

```bash
nm main.o -u | grep c_add
#                  U c_add            ✅ 对上了
```

> 这就是为什么所有 C 库头文件里都有那段：
> ```c
> #ifdef __cplusplus
> extern "C" {
> #endif
> ... 声明 ...
> #ifdef __cplusplus
> }
> #endif
> ```

### ❌ 错误 4：全局变量在头文件里"定义"了

把 `math_utils.h` 的

```cpp
extern int g_callCount;    // 声明
```

改成

```cpp
int g_callCount;           // 定义！每个 include 它的 .cpp 都定义一份
```

```bash
g++ main.o math_utils.o -o app
# math_utils.o:(.bss+0x0): multiple definition of `mu::g_callCount';
#   main.o:(.bss+0x0): first defined here
```

**看符号：**

```bash
nm -C main.o math_utils.o | grep g_callCount
# main.o:       0000000000000000 B mu::g_callCount   ← 强符号
# math_utils.o: 0000000000000000 B mu::g_callCount   ← 强符号 → 撞车
```

**规则：**

| | 强符号（`T`/`B`/`D`） | 弱符号（`W`/`V`） |
|---|---|---|
| 来源 | 普通函数、全局变量定义 | `inline` 函数、模板实例、`__attribute__((weak))` |
| 多份同名 | ❌ multiple definition 报错 | ✅ 链接器任选一份，其余丢弃 |

这正是为什么 `mu::twice`（inline）在两个 `.o` 里都存在却不报错 —— 它是 `W`。

**修复方式：**
- 头文件里只 `extern int g_callCount;`，在**一个** `.cpp` 里 `int mu::g_callCount = 0;`
- 或 C++17 起：头文件里写 `inline int g_callCount = 0;`（`inline` 变量 → 弱符号）

### ❌ 错误 5：只声明了类的成员函数，忘了实现

```cpp
class Counter {
public:
    void reset();     // 声明了，但 .cpp 里没写实现
};
```

只要 `main.cpp` 调用了 `c.reset()`：

```
undefined reference to `mu::Counter::reset()'
```

```bash

#   U mu::Counter::reset()

nm -C math_utils.o --defined-only | grep reset
#   (什么都没有)  ← 真的没实现
```

> `undefined reference to 'vtable for mu::Counter'`（符号是 `_ZTVN2mu7CounterE`）。
> 看到 `vtable for XXX` 未定义 → **99% 是某个虚函数没实现**。

## 6. 静态库 `.a`：为什么**链接顺序**会影响结果

### 打包成静态库

```bash
g++ -c math_utils.cpp -o math_utils.o
ar rcs libmu.a math_utils.o        # .a 本质就是一堆 .o 的压缩包
ar t libmu.a                       # 看里面有哪些成员
# math_utils.o
```

### ✅ 正确顺序

```bash
g++ main.o -L. -lmu -o app         # 使用者在前，库在后
```

### ❌ 错误顺序

```bash
g++ -L. -lmu main.o -o app
# undefined reference to `mu::add(int, int)'
```

### 为什么？链接器是**从左到右扫一遍**，维护一个"未解决符号集合"

```
情况 A：  g++ main.o -lmu        ✅
─────────────────────────────────────────────────────
 扫 main.o   → 待解决集合 = { mu::add(ii), mu::add(dd), Counter::…, printf }
 扫 libmu.a  → "我库里的 math_utils.o 能解决集合里的东西吗？"
               能！→ 把 math_utils.o 抽出来加入链接
               待解决集合 = { printf }
 扫 libc     → 解决 printf
 结束，集合为空 → 成功 🎉


情况 B：  g++ -lmu main.o        ❌
─────────────────────────────────────────────────────
 扫 libmu.a  → 待解决集合 = { } 空的！
               "没人需要我，math_utils.o 我就不拿了" → 整个库被跳过
 扫 main.o   → 待解决集合 = { mu::add(ii), ... }
 结束，集合非空 → undefined reference 💥
               （libmu.a 已经扫过去了，不会回头）
```

**口诀：依赖关系"被依赖者放右边"。互相依赖时可以重复写，或者用 `--start-group`：**

```bash
g++ main.o -Wl,--start-group -la -lb -Wl,--end-group -o app
```

> 另外注意：静态库是**按 .o 为单位**抽取的。如果 `libmu.a` 里有 100 个 `.o`，你只用到 1 个，最终只链进来 1 个（想全部链进来要用 `-Wl,--whole-archive`）。

## 7. 动态库 `.so`：符号在**运行时**才最终确定

```bash
g++ -fPIC -shared math_utils.cpp -o libmu.so
g++ main.cpp -L. -lmu -o app_dyn
```

直接跑会失败：

```bash
./app_dyn
# ./app_dyn: error while loading shared libraries: libmu.so: cannot open shared object file
```

因为链接时只是记下"我需要 libmu.so"，真正找库是运行时的事：

```bash
ldd app_dyn                 # 看依赖
#   libmu.so => not found   ← 运行时找不到

LD_LIBRARY_PATH=. ./app_dyn # 告诉动态加载器去哪找
# ✅ 跑通
```

### 动态库的符号表有两个

```bash
nm -C libmu.so  --defined-only     # .symtab  静态符号表（strip 后会消失）
nm -CD libmu.so --defined-only     # .dynsym  动态符号表（运行时用，strip 不掉）
readelf -sW --dyn-syms libmu.so | grep -v UND | grep GLOBAL
```

### 运行时是怎么找的？PLT + GOT（懒绑定）

```
 程序启动前（还没调用过 mu::add）
 ┌──────────────┐        ┌──────────────┐       ┌─────────────────┐
 │  app .text   │        │  PLT (跳板)  │       │  GOT (地址表)    │
 │              │        │              │       │                 │
 │ call add@plt ├───────▶│ jmp *GOT[n]  ├──────▶│ GOT[n] = 解析器  │
 │              │        │ push n       │       │                 │
 └──────────────┘        │ jmp resolver │       └─────────────────┘
                         └──────────────┘
                                 │
     第一次调用 → 动态链接器 ld-linux.so 出手：
     在已加载的 libmu.so 的 .dynsym 里查找字符串 "_ZN2mu3addEii"
     找到真实地址 0x7f... → 写回 GOT[n]
                                 │
                                 ▼
 第二次以后：call add@plt → jmp *GOT[n] → 直接命中真实地址（零开销）
```

**想亲眼看这个过程？**

```bash
LD_LIBRARY_PATH=. LD_DEBUG=bindings ./app_dyn 2>&1 | grep 'mu::\|_ZN2mu'
# binding file ./app_dyn to ./libmu.so: normal symbol `_ZN2mu3addEii'
```

`LD_DEBUG` 的其他好用取值：`libs`（看库搜索路径）、`symbols`、`all`、`help`。

### 静态链接 vs 动态链接对比

| | 静态库 `.a` | 动态库 `.so` |
|---|---|---|
| 符号何时解析 | **链接时**全部定死 | 链接时检查 + **运行时**真正绑定 |
| 符号"填空" | 直接改代码里的 `00 00 00 00` | 通过 PLT/GOT 间接跳转 |
| 缺符号的报错 | 编译期 `undefined reference` | 可能**运行期**才炸：`symbol lookup error` |
| 换库要不要重新编译 | 要 | 不要（ABI 兼容的话） |

> ⚠️ 新手常见坑：`.so` 默认允许未定义符号，所以链接时不报错，**跑起来才崩**。
> 加 `-Wl,--no-undefined` 可以让缺符号在编译 `.so` 时就报错。

## 8. 弱符号补充实验：inline / 模板为什么不会"撞车"

```bash
nm -C main.o math_utils.o | grep -E 'twice|maxOf'
```

```
main.o:       0000000000000000 W mu::twice(int)
main.o:       0000000000000000 W int mu::maxOf<int>(int, int)
math_utils.o: 0000000000000000 W mu::twice(int)
math_utils.o: 0000000000000000 W int mu::maxOf<int>(int, int)
```

**两个 `.o` 各有一份，但链接不报错**，因为它们在 `.section .text._ZN2mu5twiceEi,"axG",@progbits,...,comdat` 这种 **COMDAT 组**里，标记为弱符号 → 链接器去重，只留一份。

```bash
nm -C app | grep -E 'twice|maxOf'
# 0000000000001310 W mu::twice(int)                 ← 只剩一份
# 0000000000001326 W int mu::maxOf<int>(int, int)
```

**这就是 ODR（One Definition Rule）在链接层面的实现**，也是为什么：
- ✅ 模板、`inline` 函数、`constexpr` 函数、类内定义的成员函数 → **可以**放头文件
- ❌ 普通函数、普通全局变量 → **不能**放头文件（会 multiple definition）

## 10. 排错决策树（贴墙用）

```
链接/运行报错
    │
    ├─ "undefined reference to `X'"  （链接期）
    │     │
    │     ├─ 1. nm -C -u *.o | grep X        → 确认谁在要
    │     ├─ 2. nm -C --defined-only *.o *.a | grep X   → 谁能给
    │     │      ├─ 没人给 → 忘写实现 / 忘编译某个 .cpp
    │     │      ├─ 有人给但签名不同 → 少 const？参数类型不对？命名空间不对？
    │     │      └─ 有人给但在库里 → 3.
    │     ├─ 3. 库放在使用者右边了吗？   g++ main.o -lmu  ✅
    │     ├─ 4. 符号名一个带 _Z 一个不带 → 缺 extern "C"
    │     └─ 5. "undefined reference to `vtable for X'" → 有虚函数没实现
    │
    ├─ "multiple definition of `X'"  （链接期）
    │     └─ 头文件里定义了普通函数/全局变量 → 加 inline，或挪到 .cpp
    │
    ├─ "cannot open shared object file"  （运行期）
    │     └─ ldd app  → LD_LIBRARY_PATH / rpath / ldconfig
    │
    └─ "symbol lookup error: undefined symbol: X"  （运行期）
          └─ .so 版本不对 / 符号被 hidden
             nm -CD lib.so | grep X
             readelf -sW lib.so | grep X    看是不是 HIDDEN/LOCAL
```

## 12. 三句话总结

1. **编译阶段**：每个 `.cpp` 独立编译成 `.o`，把自己有的东西记在**符号表**（`T`/`B`/`W`），把自己缺的记成 `U`，并在**重定位表**里写明"缺的东西要填在第几个字节"，代码里先放 `00 00 00 00` 占位。
2. **符号名**必须把命名空间/类/函数名/参数类型/const 全编码进去（mangling），因为这是 `.cpp` 之间唯一的通信语言 —— 这也是重载能工作、以及签名写错就"找不到"的根本原因。
3. **链接阶段**：合并段 → 分配真实地址 → 按重定位表把占位符**回填**成真地址。所有 `undefined reference` 都是"某个 `U` 没找到对应的 `T`"，用 `nm -C -u` 和 `nm -C --defined-only` 两条命令对比一下，原因立刻现形。
