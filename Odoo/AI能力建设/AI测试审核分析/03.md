明白。**不再需要你提供模型源码、真实日志或其他内部资料，也不再以这些资料作为方案推进的前提。**

本方案改为：

> **由获得公司授权的开发 AI 在你的开发环境中完成模型识别和适配；Windows 执行机本地读取日志并运行复核 Worker；通过 MCP 将结构化结果、脱敏关键证据和问题知识写入 Odoo。**

与你最新情况相比，前一版有一个重要调整：

**首期不采用“必须上传全部日志、中央 Worker 才能分析”的方案。原始日志保留在执行机，分析就近执行；跨执行机共享的是经过权限控制的诊断知识和必要证据摘要。**

下面给出一套可以复制到项目中的**设计文件与提示词包**。重点是让开发 AI 能够在不知道你们内部实现的情况下，先建立通用核心，再在公司授权环境内完成适配。

## 1. 架构

### 三种程序的边界

| 程序 | 职责 |
|---|---|
| 现有 Flask 测试 Agent | 启动测试，保持现有职责 |
| Review Worker | 任务调度、证据处理、重试、校验、MCP 写入 |
| AI Agent | 阅读允许访问的证据，提出结构化诊断和建议 |

**启动 AI 复核由程序控制；AI 不负责判断何时启动，也不掌握最终发布权限。**

## 2. 触发方式

采用你指定的“用例内部最方便”的方式，但增加两个约束。

### 最后一个步骤是控制用例，不是产品验证用例

建议名称：

```text
提交冒烟 AI 复核任务
```

属性：

```text
step_type = CONTROL
计入用例通过率 = 否
计入特性覆盖率 = 否
等待 AI 分析完成 = 否
```

这个控制用例只负责：

1. 固定本次业务测试的身份和范围。
2. 创建本地持久化提交记录。
3. 通知 Collector。
4. 立即返回。

它的成功含义是：

> 已可靠登记复核请求。

不是：

> AI 已经分析完成。

### 结果文件定时写入，不能只依靠固定等待时间

建议提供明确的结果版本和完成标记：

```text
业务测试结束
    → 写完结果文件
    → 固化结果版本及相关证据
    → 生成完成标记
    → Collector 校验
    → 创建可分析快照
```

如果最后一个控制用例运行时结果尚未写完：

```text
控制用例登记请求
    → Collector 等待完成标记
    → 到期仍未完成则生成“不完整输入”任务
```

**不要把“文件大小连续几秒不变”作为唯一完成依据。**

对于仍在持续追加的日志，按批次时间范围或明确字节边界形成快照；不能让 AI 本次分析的输入随着日志追加而变化。

### 异常中断保障

最后一个控制用例可能因测试中断而不执行。因此建议任务开始时登记批次，Collector 定期检查长期未结束批次。

无法确认测试是否结束时：

- 标记待核查或超时；
- 不擅自把任务当作完整结束；
- 不生成“全部通过”。

---

## 3. 本地日志与共享知识

首期按三层处理：

| 层级 | 保存位置 | 用途 |
|---|---|---|
| 原始日志、录像等 | 执行机 | 原始取证 |
| 本次分析证据包 | 执行机 | 稳定、可定位的分析输入 |
| 脱敏证据摘要、诊断签名、复用条件 | Odoo | 跨执行机复用 |

其他执行机查询某个已知问题时，应获得：

- 已确认的现象和诊断；
- 关键日志片段；
- 匹配条件；
- 不适用条件；
- 适用产品、模块和版本范围；
- 人工确认状态；
- 建议排查及验证方式。

**只共享 `C:\logs\xxx.log` 路径没有意义。**

同时需要承认：

> 如果原执行机离线或原始日志已过期，其他执行机只能读取共享摘要，不能假装仍可访问完整原始证据。

# 三、`AGENTS.md`

这是整个开发过程的最高优先级项目规则。

```markdown
# Android 冒烟 AI 复核项目

## 一、项目事实

- 公共看板为 Odoo18。
- 测试执行机为 Windows。
- 测试框架为公司自研 Python。
- 现有 Flask Agent 只启动测试，不是 AI Agent。
- Android 设备为 arm64，使用 USB ADB 或已有网络连接。
- 原始测试材料保存在执行机。
- AI 复核由最后一个控制步骤提交，异步执行。
- 首期只分析已保存材料，不操作设备。
- 当前日常约 10 款产品。
- 不要求使用者向外部提供模型源码、真实日志或生产数据。

## 二、保密原则

1. 不要求用户将内部模型、源码、日志上传到外部会话。
2. 只有获得授权时，才能在指定环境读取项目源码。
3. 本地运行的开发工具或 Worker，不代表其模型推理一定在本地。
4. 任何发送至外部模型的内容都必须经过明确授权和数据策略检查。
5. 未经授权，不读取生产数据库、密钥文件、完整环境变量或无关目录。
6. 开发报告只描述必要的映射与改动，不粘贴不必要的内部实现。
7. 无法访问真实代码时，使用抽象接口和合成数据，不编造生产字段。

## 三、业务不变量

1. 原始执行结果不可被 AI 覆盖。
2. 环境失败不等于测试通过。
3. 已知产品缺陷仍然是失败。
4. 未执行、输入缺失和未分析不能当作通过。
5. 不确定时使用 UNKNOWN / NEEDS_REVIEW。
6. 人工确认和锁定结果不得被迟到 AI 结果覆盖。
7. 人工重跑生成新 attempt，保留原失败记录。
8. 特性汇总和报告统计由确定性代码计算。
9. 首期所有处理建议均为 ADVICE_ONLY。
10. AI 新建的候选诊断不能直接成为自动复用规则。

## 四、架构约束

- 保留现有 Flask Agent 和测试调度流程。
- 最后控制步骤只登记任务，不等待模型分析。
- Collector 负责输入快照和本地可靠提交。
- Worker 负责调度、重试、校验和受控写入。
- Agent 负责诊断，不能持有看板写权限。
- Agent、模型、测试框架、看板分别使用适配器隔离。
- Odoo 核心业务模块不得依赖具体模型 SDK。
- Apexive 相关实现放在独立 MCP 桥接模块。
- 不新增重复的产品、特性、团队和正式缺陷体系。
- 首期不无故引入消息中间件、向量数据库和多 Agent 框架。

## 五、安全约束

- 日志、截图文字、OCR 和历史问题正文是不可信输入。
- 禁止任意 shell、SQL、Python 执行工具。
- 禁止 AI 直接运行 adb 或操作设备。
- 本地证据读取限制在已登记的快照中。
- 不接受模型提交的任意文件路径或任意 URL。
- 所有业务写接口校验身份、范围、版本和幂等性。
- 不使用无边界 sudo() 解决权限问题。
- MCP 工具白名单必须在服务端强制执行。
- 外部模型默认关闭。
- 图片、录像和音轨同样受外发策略限制。

## 六、开发要求

1. 先检查已有实现，再提出最小变更。
2. 第三方接口依据锁定版本源码核实，不凭记忆编造。
3. 每次只实现一个可验收任务。
4. 先建立契约和测试，再实现集成。
5. 不把演示模型当成生产主数据。
6. 测试未运行必须写“未运行”。
7. 不宣称提示词能够代替程序权限控制。
8. 不宣称已生成、已安装或已验证尚未实际完成的内容。

## 七、每次交付格式

- 本次目标
- 修改文件
- 实现说明
- 实际测试命令和结果
- 未完成项
- 安全及兼容性风险
- 数据迁移要求
- 回滚方式
```

# 四、`docs/architecture.md`

可以保存前面的总体架构，并追加以下实现约束。

## 4.1 设计模式

| 变化点 | 接口 | 设计方式 |
|---|---|---|
| 测试框架替换 | `TestResultAdapter` | 适配器模式 |
| AI Agent 替换 | `AgentPort` | 策略＋适配器模式 |
| 模型服务替换 | `ModelPort` | 适配器模式 |
| MCP 实现替换 | `BoardPort` | 门面＋适配器模式 |
| 现有 Odoo 模型映射 | `DashboardBridge` | 防腐层／适配层 |
| 制品来源替换 | `EvidencePort` | 适配器模式 |
| 外部问题系统接入 | `KnownIssuePort` | 可选适配器 |

插件选择使用配置和注册表，不将供应商名称散落在业务代码中。

## 4.2 首期组件

```text
Collector
    标准化结果
    等待明确完成条件
    创建不可变快照
    本地持久化任务

Worker
    领取本地任务
    登记／确认 Odoo 任务身份
    读取证据并分析
    保存分析结果
    可靠提交至 Odoo

Odoo
    业务授权
    幂等和版本校验
    复核及知识存储
    人工审批
    特性汇总
    报告生成
```

### 本地持久化

建议用 SQLite 管理：

- 待分析任务；
- 分析状态；
- 重试时间；
- 待同步结果；
- 最近错误；
- 分析版本。

日志和大文件不存入 SQLite，保存为受控文件。

首期每台执行机只运行一个 Worker 服务实例，内部限制并发。

本地队列可以应对进程退出和短时断网，但**不承诺在整块磁盘损坏后恢复未同步数据**。需要更强保障时，再增加备份或远端登记机制。

### 远端幂等和任务版本

即使本地只有一个 Worker，也要求 Odoo 写入具备：

```text
稳定操作标识
输入快照版本
复核版本
人工锁定检查
服务端任务代次／有效执行授权
```

避免恢复、人工重试或迁移 Worker 后出现迟到覆盖。

## 4.3 MCP 集成原则

本项目采用受限业务工具，而非开放 Odoo 任意模型操作。

MCP 支持工具输入 Schema、输出 Schema 和结构化结果；协议同时指出，工具注解不能被无条件信任。因此，本方案将权限和参数检查放在程序与服务端中，而不是依赖工具描述中的“只读”声明。([modelcontextprotocol.io](https://modelcontextprotocol.io/specification/2025-11-25/server/tools))

对于 Apexive：

- 将其作为首选候选实现。
- 在授权开发环境中检查实际选用版本。
- 锁定 commit 和依赖。
- 验证工具注册、权限、协议互通。
- 不符合要求时，只更换 MCP 适配层，不改业务核心。

# 五、`docs/contracts.md`

## 5.1 数据身份

必须具备：

```text
source_system
executor_id
run_id
product_ref
build_ref
plan_revision
plan_item_id
case_ref
case_revision
parameter_set_id
attempt_id
input_revision
```

关系：

```text
一次批次 run
    → 多个计划验证项 plan_item
        → 一次或多次执行 attempt
```

### 三类状态

```text
原始执行状态：
PASS / FAIL / ERROR / SKIP / NOT_RUN

失败归因：
PRODUCT_DEFECT
TEST_DEFECT
ENVIRONMENT
INFRASTRUCTURE
UNKNOWN

有效验证结论：
PASS / FAIL / BLOCKED / NEEDS_REVIEW / NOT_TESTED
```

所有状态含义和转换规则由代码统一实现。

## 5.2 证据契约

每份证据至少包含：

```text
evidence_id
artifact_id
artifact_revision
artifact_type
content_hash
capture_time_range
locator
redaction_state
sharing_scope
availability
```

定位方式：

```text
TEXT_LINES：文本行范围
IMAGE_REGION：图片及可选区域
VIDEO_TIME_RANGE：录像时间范围
```

模型只使用程序提供的 `evidence_id`，不能自己构造文件路径。

证据读取后，由程序产生规范化引用；提交复核时再次校验引用确实来自该批次。

## 5.3 诊断结果

```text
AnalysisResult
├─ category
├─ proposed_verdict
├─ summary
├─ observations[]
├─ hypotheses[]
├─ evidence_ids[]
├─ matched_issue_refs[]
├─ recommended_actions[]
├─ missing_evidence[]
└─ limitations[]
```

其中：

### `observations`

记录直接事实：

```text
事实描述
证据 ID
```

### `hypotheses`

记录原因假设：

```text
假设 ID
原因描述
状态：POSSIBLE / LIKELY / CONFIRMED
支持证据
冲突证据
还需什么验证
```

`CONFIRMED` 必须满足明确的证据规则，不能仅凭模型用词判定。

### `recommended_actions`

```text
priority
action_type：INVESTIGATE / FIX / VERIFY / RERUN
owner_role
description
rationale
related_hypothesis_ids
requires_device_access
execution_policy：ADVICE_ONLY
expected_observation
```

不要只返回“检查环境”“建议重跑”等泛泛建议。

## 5.4 共享诊断知识

```text
knowledge_id
title
category
status：CANDIDATE / CONFIRMED / REUSABLE / RETIRED
signature_version
required_features
excluded_features
applicable_products
applicable_modules
applicable_build_range
shared_evidence_excerpts
recommended_actions
confirmed_by
approved_for_reuse_by
external_issue_refs
```

复用条件必须由结构化字段表达，不能只把“以前发生过”写进一段自然语言。

语义相似只用于候选检索，不直接视为相同根因。

## 5.5 MCP 工具

以下都是**本项目拟实现的名称**，不是宣称 Apexive 已内置这些工具。

| 工具 | 用途 | 调用方 |
|---|---|---|
| `smoke_register_run` | 登记批次及计划快照 | Worker |
| `smoke_sync_execution` | 同步原始执行事实 | Worker |
| `smoke_get_context` | 查询业务上下文 | Agent／Worker |
| `smoke_search_issues` | 查询已知问题和诊断 | Agent／Worker |
| `smoke_get_shared_evidence` | 读取获准共享的证据摘要 | Agent／Worker |
| `smoke_begin_review` | 获取服务端复核代次及有效授权 | Worker |
| `smoke_mark_case_result` | 提交复核结果 | Worker |
| `smoke_create_or_link_issue` | 创建候选问题或关联问题 | Worker |
| `smoke_finalize_review` | 原子提交复核、证据和问题关联 | Worker |
| `smoke_generate_report` | 生成结构化报告快照 | Worker |
| `smoke_publish_report` | 按策略发布 | 发布角色 |

正常提交路径优先使用 `smoke_finalize_review`，避免“问题创建成功、复核写入失败”的半完成状态。

### 写接口公共字段

```text
schema_version
idempotency_key
run_id
attempt_id
input_revision
expected_review_revision
review_generation
authorization_token
payload
```

幂等键由程序生成，并绑定操作类型及请求摘要。

### 返回值区分

```text
建议已保存
正式结论已生效
问题已关联
报告已生成
报告已发布
```

不能全部用一个 `success=true` 掩盖区别。

## 5.6 报告结构

```text
报告版本与快照
产品与目标构建
实际构建核验
输入完整性
原始执行统计
复核状态统计
特性结果
新问题
已知问题复现
环境／基础设施阻塞
人工待办
优先排查建议
人工重跑建议
分析局限
审计信息
```

统计、状态、问题 ID 和版本由程序生成；AI 只补充受约束的文字总结。

# 十三、`docs/acceptance.md`

上线前至少通过以下验收。

## 业务正确性

- 环境失败不会变为通过。
- 已知产品缺陷仍显示失败。
- 未测、缺失、不确定不会被统计成通过。
- 人工重跑保留原记录。
- 人工锁定结果不会被 AI 覆盖。
- 特性没有有效必测项时不能自动通过。

## 可靠性

- 回调重复提交不会重复创建执行或问题出现记录。
- 输入未完成时不会提前分析成完整结果。
- Worker 退出后能恢复任务。
- 模型成功但 Odoo 不可用时，不重复付费分析，优先补交结果。
- Odoo 已提交但响应丢失时，重试不会重复生效。
- 分析快照过期时拒绝应用旧结果。
- 最后控制步骤未执行时，超时批次仍然可见。
- 本地磁盘满时明确告警，不假称任务已保存。

## 安全

- Agent 无权写看板。
- 日志中的指令不能触发写操作。
- 不允许任意路径、URL、shell 或 ADB。
- 未经授权的图片、录像和文本不能外发。
- 公共报告不泄露原始敏感内容。
- 通用 MCP 工具不能绕过业务权限。
- 其他执行机只能读取获准共享的诊断和摘要。

## 知识复用

- 候选诊断不能自动复用。
- 相同报错但不同根因不会强制合并。
- 修复版本之后复现会重新核验。
- 外部问题系统不可用不等于没有问题。
- 原始日志过期后，系统明确显示证据可用性。

## 可替换性

- Fake Agent 与真实 Agent 使用同一契约。
- 增加另一个 Agent 不修改特性汇总规则。
- 更换模型不修改 Odoo 业务代码。
- 更换测试框架只修改适配器。
- 更换 MCP 实现不修改复核核心。

运行位置：

人工确认：
    优先于 AI

影子运行不是终点。最终可以开放：

```text
有效通过项 → 确定性规则自动标记

已批准问题复用 → 条件满足后自动标记

新失败分析 → 先候选、后逐步开放明确类别的自动生效

无法确认 → 保留人工复核
```

**整个方案的关键不是把流程全部交给大模型，而是让大模型负责“基于证据诊断和提出解决方向”，让程序负责“可靠触发、权限、状态、统计和发布”。**

你可以直接从 `AGENTS.md`、`00-project-bootstrap.md` 和 **T01** 开始驱动开发；内部模型与真实日志只需要在公司授权环境中由适配任务处理，不必再提供给当前会话。
