你的回答已经足够确定**首期架构、业务边界和开发顺序**，不需要继续进行大范围需求访谈。

现在还缺的是现有系统的实际接口和字段，而不是业务方向。因此可以开始开发通用核心，把与现有 Odoo、测试框架有关的部分留在适配层。

根据你的补充，我调整三点：

1. **AI 不只判断失败类型，还必须给出有证据支持的排查与解决方向。**

3. **允许以“最后一个测试步骤”触发复核，但该步骤只负责可靠提交任务，不等待 AI 分析完成。**

# 一、冻结的技术方案

建议保存为：`docs/01-scope-and-decisions.md`

## 1.1 首期范围

| 项目 | 已确定方案 |
|---|---|
| 测试框架 | 自研 Python，输出统一 JSON |
| 测试设备 | Android arm64，通过 USB ADB／网络连接 |
| 证据来源 | 已保存的用例日志、logcat、串口日志、截图、录像、tombstone、ANR、刷机日志 |
| 设备操作 | AI 首期不操作设备，不重跑、不重连、不重启、不刷机 |
| 规模 | 当前约 10 款产品；并发量通过试运行测量 |
| 触发方式 | 完成回调优先；兼容最后一个控制步骤触发 |
| Odoo | 复用既有产品、特性、团队、问题和日报模型 |
| MCP | 优先验证 Apexive，单独封装桥接模块 |
| AI 实现 | 独立 Python Worker，Agent 和模型均可替换 |
| 知识积累 | 从新产生的分析和人工确认开始积累 |
| 外部问题系统 | 首期非必需，预留只读查询及关联接口 |
| 环境失败 | 阻塞，提供排查方向；人工决定是否重跑 |
| 上线方式 | 先影子运行，再开放受控自动标记 |
| 中间件 | 首期不引入额外消息中间件、向量数据库 |

## 1.2 必须区分的三个结果

```text
原始执行结果
    测试框架报告了什么？

AI 复核结论
    失败更可能是什么原因？有哪些证据？

有效验证结果
    这个用例／特性最终是否被有效验证？
```

例如：

```text
原始执行结果：FAIL
AI 归因：ENVIRONMENT
有效验证结果：BLOCKED
建议：人工检查供电及 USB 连接，再按调度流程重跑
```

**不能把环境失败改写成原始 PASS，也不能仅因为“不是代码问题”就将特性标绿。**

## 1.3 首期 AI 的交付标准

对于需要分析的失败，AI 至少回答：

1. 直接观察到了什么？
2. 最可能属于哪类问题？
3. 哪些证据支持这个判断？
4. 还有哪些合理的替代解释？
5. 优先检查什么，为什么？
6. 怎样验证问题是否解决？
7. 当前缺少什么材料？

不要求 AI 在证据不足时给出确定根因。

# 二、总体架构与部署

建议保存为：`docs/02-architecture.md`

## 2.1 架构图

```text
现有任务下发系统
       │
       ▼
Windows Flask 测试 Agent
       │
       ▼
自研 Python 测试框架 ──────► Android 设备
       │
       ├─ 原有结果回传：保持不变
       │
       └─ 完成钩子／最后控制步骤
                    │
                    ▼
           Collector 结果采集器
            ├─ 输出标准 JSON
            ├─ 制品登记与上传
            ├─ 本地持久化补传
            └─ 提交批次封存请求
                    │
                    ▼
                Odoo18
            ├─ 既有看板业务模型
            ├─ 复核任务与审计
            ├─ 诊断知识和问题关联
            ├─ 特性汇总
            ├─ 人工确认
            └─ 报告快照
                    ▲
                    │ MCP
                    ▼
          独立 Python Review Worker
            ├─ 领取任务／续租
            ├─ 获取证据
            ├─ 检索历史诊断
            ├─ 调用可替换 Agent
            ├─ 校验结论
            └─ 提交复核结果

共享制品存储
    └─ 保存日志、截图、录像等；Odoo 保存引用和元信息
```

## 2.2 推荐部署

**默认选择：集中部署一个 Review Worker 服务。**

理由是首期不操作设备，分析过程没有必须运行在执行机上的要求。建议从一个 Worker 进程、较小并发开始测量。

但保留以下能力：

```text
同一套 Worker
    可以部署在中央服务器
    也可以部署在 Windows 执行机
```

部署位置不影响业务接口和问题复用机制。

如果暂时没有共享存储，可以先采用：

```text
Windows Collector
    → 上传到公司现有文件服务器
    → Worker 通过受控接口读取
```

不要让其他执行机依赖某台 Windows 的本地绝对路径。

## 2.3 四个核心隔离接口

| 接口 | 隔离什么 | 推荐模式 |
|---|---|---|
| `TestResultAdapter` | 自研测试框架及未来替换框架 | 适配器模式 |
| `AgentPort` | 不同 AI Agent 实现 | 策略＋适配器模式 |
| `ModelPort` | 不同模型服务 | 适配器模式 |
| `BoardPort` | MCP 客户端与看板业务交互 | 门面＋适配器模式 |

还应保留：

- `ArtifactPort`：制品存储。
- `KnownIssuePort`：外部问题系统。
- `DashboardBridge`：现有 Odoo 模型映射。

### Agent 与模型分开替换

两者不是同一个变化点：

```text
Agent：
    如何组织检索、阅读证据、调用工具和输出结论。

模型：
    实际使用哪个推理服务。
```

首期推荐：

> **受限工具循环的单 Agent＋确定性工作流，不引入多 Agent 协作框架。**

Agent 可以按需读取更多日志，但只允许使用只读工具。写入和发布由 Worker 的确定性代码执行。

## 2.4 Odoo 模块划分

```text
smoke_ai_core
    复核任务、复核记录、诊断知识、规则、报告快照
    不依赖 Apexive 或模型 SDK

smoke_ai_ingest
    Collector 接入、批次封存、制品登记

smoke_ai_mcp
    Apexive 工具注册与调用边界

smoke_ai_dashboard_bridge
    扩展你现有看板模型

smoke_ai_demo
    仅开发／测试使用的假业务数据与演示映射
```

`smoke_ai_demo` 不作为生产业务模型替代品。

# 三、任务触发：支持“最后一个用例”，但不能直接等待 AI

建议保存为：`docs/03-trigger-and-lifecycle.md`

这是你补充后需要重点明确的地方。

## 3.1 推荐方式

```text
测试执行完毕
    → 关闭并固化日志
    → 标准化结果
    → 本地持久化待提交任务
    → 上传证据
    → 请求封存
    → 创建复核任务
    → Worker 异步分析
```

**测试流程不等待模型调用完成。**

否则 AI 服务故障、网络波动或分析耗时，会影响测试任务结束和下一轮设备调度。

## 3.2 “最后一个用例”方案

可以实现一个控制步骤：

```text
名称：提交冒烟 AI 复核任务
类型：CONTROL
计入产品通过率：否
计入特性覆盖率：否
```

它只完成：

1. 生成标准结果清单。
2. 将提交任务持久化到本地 spool。
3. 尝试通知采集器。
4. 返回“复核提交已登记”状态。

需要明确：

> 这个步骤成功，只表示提交工作已可靠登记，不表示 AI 已经分析完成。

如果连本地持久化都失败，应上报基础设施告警，不能假称提交成功。

## 3.3 避免循环依赖

不能出现：

```text
AI 触发用例等待测试完成
测试完成又等待 AI 触发用例结束
```

解决方式：

- 业务测试结果清单排除 `CONTROL` 步骤。
- 触发步骤只消费已经结束的业务测试结果。
- 最终封存由测试框架结束钩子或 Collector 完成。
- AI 分析状态单独显示，不混入产品用例通过率。

## 3.4 不能只依赖最后一步

如果刷机失败、测试进程崩溃或任务被取消，最后一步可能根本没有执行。

因此需要三层保障：

| 路径 | 用途 |
|---|---|
| 正常完成回调／结束钩子 | 主路径 |
| 最后控制步骤 | 兼容无法方便增加回调的情况 |
| 超时对账 | 查找长期未封存、取消或异常中断任务 |

超时对账可以由现有任务系统或轻量定时任务完成，不需要新增消息中间件。

## 3.5 分开保存生命周期

不要把所有状态塞进一个字段。

```text
input_state：
    OPEN / SEALED_COMPLETE / SEALED_PARTIAL

review_state：
    PENDING / RUNNING / COMPLETED / NEEDS_HUMAN / FAILED

publication_state：
    DRAFT / PUBLISHED / SUPERSEDED
```

`SEALED_PARTIAL` 表示批次输入已停止接收本版本数据，但明确有缺失。

它仍然可以生成报告，只是报告必须显示缺失和阻塞，不能变成完整通过。

# 四、统一数据契约

建议保存为：`docs/04-contracts.md`

## 4.1 身份与粒度

建议增加一个重要标识：`plan_item_id`。

```text
run_id
    一次产品冒烟批次

plan_item_id
    该批次要求完成的一个验证项
    包含用例、参数、设备要求等维度

attempt_id
    某验证项的一次实际执行
```

关系：

```text
一个 run
    有多个 plan_item

一个 plan_item
    可以有多次 attempt
```

这样才能正确处理：

- 参数化用例。
- 多设备验证。
- 人工重跑。
- 缺失用例。
- 特性覆盖率。

所有外部标识应携带来源系统命名空间，不能直接假定不同系统的数字 ID 不会重复。

## 4.3 分析结果契约

在上一版基础上，将“推荐动作”从字符串升级为结构化对象：

```text
AnalysisResult
├─ category
├─ proposed_verdict
├─ summary
├─ observations[]
├─ evidence_refs[]
├─ hypotheses[]
├─ recommended_actions[]
├─ missing_evidence[]
└─ matched_issue_refs[]
```

### 核心字段定义

| 字段 | 内容 |
|---|---|
| `observations` | 直接从材料看到的事实 |
| `hypotheses` | 原因假设及支持／反对证据 |
| `recommended_actions` | 排查、修复或验证建议 |
| `missing_evidence` | 无法进一步判断所缺材料 |
| `matched_issue_refs` | 已知诊断或外部问题关联 |

### 原因假设

```json
{
  "id": "H1",
  "description": "USB 链路异常可能导致连接中断",
  "status": "POSSIBLE",
  "supporting_evidence_ids": ["E1"],
  "contradicting_evidence_ids": [],
  "verification": "结合已保存的主机 USB 事件与设备侧日志确认中断先后顺序"
}
```

### 处理建议

```json
{
  "priority": 1,
  "type": "INVESTIGATE",
  "owner_role": "TEST_ENGINEER",
  "description": "先检查现有主机连接日志，确认是否发生 USB 设备移除或重枚举",
  "rationale": "当前只有 ADB 断连现象，尚不能区分链路异常与设备系统异常",
  "related_hypothesis_ids": ["H1"],
  "requires_device_access": false,
  "requires_human": true,
  "execution_policy": "ADVICE_ONLY",
  "expected_observation": "获得可与设备日志对齐的连接事件时间线"
}
```

所有动作在首期均为：

```text
execution_policy = ADVICE_ONLY
```

即使 AI 建议“重跑”，也只是给人工看的建议，不能自动转换成设备操作。

## 4.4 多媒体证据定位

本版不再要求所有证据都使用文本行号。

| 类型 | 定位方式 |
|---|---|
| 文本日志 | 制品版本＋行范围 |
| 截图 | 制品版本＋可选区域 |
| 录像 | 制品版本＋时间范围 |
| 录像抽帧 | 父录像引用＋时间戳＋派生图片引用 |
| tombstone／ANR 文本 | 制品版本＋行范围／段落标识 |

建议证据引用使用判别联合类型：

```text
locator.type = TEXT_LINES
locator.type = IMAGE_REGION
locator.type = VIDEO_TIME_RANGE
```

必须保留原始制品与派生制品的关系，不能将 OCR 文本当成未经转换的原始日志。

# 五、AI 分析与知识积累

建议保存为：`docs/05-analysis-and-knowledge.md`

## 5.1 默认分析流程

```text
① 检查批次、执行和制品完整性
② 提取用例失败步骤与时间窗
③ 读取刷机、用例和系统日志摘要
④ 查询已确认诊断及相似问题
⑤ 判断是否满足严格复用条件
⑥ 如不满足，调用 AI 分析
⑦ 按需读取更多日志或多媒体证据
⑧ 校验结论和证据引用
⑨ 保存复核建议及问题关联
⑩ 更新人工待办或受控生效
⑪ 汇总特性结果和报告
```

默认只对以下情况调用模型：

- `FAIL`。
- `ERROR`。
- 异常 `SKIP`。
- 结果或证据矛盾。
- 规则检测到的异常。

通过项主要由确定性规则检查完整性，不必逐条调用模型。

## 5.2 多模态材料的首期处理

不建议第一版直接把完整录像全部交给模型。

建议：

1. 文本证据优先。
2. 需要时读取失败时截图。
3. 录像先按失败时间窗抽帧。
4. 无多模态模型时允许标记“图像证据未分析”。
5. 不能把“没有分析截图”写成“截图未发现异常”。

### 外发控制

“脱敏后允许外发”必须落实到不同材料：

- 文本：脱敏后再扫描。
- 截图：检查界面上的账号、设备标识和其他敏感信息。
- 录像：考虑图像和音轨。
- OCR：OCR 结果仍需脱敏。
- 历史问题：可能包含人员、地址和内部链接，同样处理。

建议首期默认：

> **未完成可靠脱敏的图片、录像和音频，不允许发送外部模型。**

不能只做文本脱敏，就认为整个证据包都可以外发。

## 5.3 冷启动知识库

你已有历史记录参考价值有限，因此建议：

```text
AI 候选诊断
    → 人工修正／确认
    → 获批的诊断知识
    → 自动复用规则
```

知识状态：

```text
CANDIDATE
CONFIRMED
REUSABLE
RETIRED
```

分别表示：

- AI 初步提出。
- 人工确认诊断。
- 满足明确条件时允许复用。
- 已失效或撤销。

**人工确认了某一次结论，不代表自动批准在所有产品、版本中复用。**

## 5.4 与外部问题系统的边界

避免建立第二套研发缺陷管理系统。

建议区分：

### 冒烟诊断记录

由本系统维护：

- 本次现象。
- 证据。
- 归因。
- 诊断签名。
- 复用条件。
- 每日出现次数。
- 排查建议。

### 正式缺陷单

优先继续由现有问题系统维护：

- 研发负责人。
- 修复流程。
- 修复版本。
- 关闭状态。

关联结构：

```text
诊断记录
    ├─ 外部系统名称
    ├─ 外部问题 ID
    ├─ 最近同步时间
    └─ 外部状态快照
```

首期可以只有关联字段；外部系统接入后，再启用查询。

外部系统不可用时，应返回：

```text
查询状态：UNAVAILABLE
```

不能返回“没有已知问题”，因为未查到与查询失败含义不同。

## 5.5 复用条件

允许跳过完整 AI 分析的条件建议为：

```text
诊断知识已批准复用
AND 必要特征匹配
AND 产品／模块／版本范围匹配
AND 必要证据完整
AND 无排除条件
AND 未超过有效期或失效条件
```

以下情况必须重新分析：

- 只有相同报错文本。
- 修复版本之后再次出现。
- 关键证据缺失。
- 产品或模块范围不匹配。
- 新证据与历史根因冲突。

### 并发去重的范围

对以下对象做严格幂等：

- 相同执行记录。
- 相同复核提交。
- 相同问题 occurrence。
- 相同受控签名键的创建。

但不要将“相同症状签名”无条件合并成同一个已确认根因。证据不足时只进行候选分组。

## 5.6 人工重跑后的处理

人工重跑必须产生新 `attempt_id`，并记录：

```text
rerun_of
rerun_reason
requested_by
```

有效结果由规则选择，不能简单采用“最后一条结果覆盖”。

建议规则：

- 同一目标构建、计划项和必要环境要求。
- 重跑完成且证据有效。
- 保留之前失败记录。
- 对疑似偶发问题显示“重跑通过／存在不稳定性”。
- 人工已锁定的结论需要显式重新审批。

# 六、Odoo、MCP 与接口设计

建议保存为：`docs/06-odoo-and-mcp.md`

## 6.1 Apexive 选型结论

可以继续作为优先验证方案，但要先在测试库验证，不直接装入生产看板。

本次核查到的 `18.0` 分支 manifest 声明了 `base`、`llm`、`llm_tool`、`web_json_editor` 依赖，以及 Python `mcp` 依赖。因此安装方案必须按实际代码与依赖锁定，而不能仅按 README 的简化说明处理。([raw.githubusercontent.com](https://raw.githubusercontent.com/apexive/odoo-llm/18.0/llm_mcp_server/__manifest__.py))

`llm_tool` 文档提供装饰器和 XML 配置两种扩展方式，也包含记录修改、删除以及模型方法执行等通用工具。**本项目应只向服务账号开放受限冒烟工具，不开放通用工具作为捷径。**([raw.githubusercontent.com](https://raw.githubusercontent.com/apexive/odoo-llm/18.0/llm_tool/README.md))

MCP 的 Streamable HTTP 有初始化、请求响应、会话及 Origin 校验等要求，应将真实客户端与服务端的互通测试列为接入验收项；不能只验证一次 HTTP 请求返回成功。([modelcontextprotocol.io](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports))

工具可以声明输入、输出 Schema；协议中的工具注解不是可信的权限边界。项目仍需由服务端实施读写授权与业务校验。([modelcontextprotocol.io](https://modelcontextprotocol.io/specification/2025-11-25/server/tools))

Odoo 官方文档也明确提醒：公开方法的参数不可直接信任，ACL 检查主要发生在 CRUD 操作时。因此 MCP 包装方法必须显式检查身份、记录范围和状态转换。([raw.githubusercontent.com](https://raw.githubusercontent.com/odoo/documentation/18.0/content/developer/reference/backend/security.rst))

### 接入验证必须记录

```text
Apexive Git commit
安装模块及版本
Python 依赖锁定文件
Odoo18 运行版本
MCP 协议协商结果
成功／失败的兼容性测试
工具授权与越权测试
```

这里不指定未经你环境验证的固定 SDK 版本。

## 6.2 不新增重复业务主数据

已有：

```text
产品
特性
团队
用例
问题
日报
```

优先复用。

新增的是原系统没有的能力：

| 能力 | 建议新增或扩展 |
|---|---|
| 复核任务、租约、重试 | 通常新增 |
| AI／人工复核历史 | 通常新增 |
| 证据引用 | 按现有附件体系扩展 |
| 诊断签名与复用条件 | 通常新增 |
| 执行与问题关联 | 按现有模型扩展 |
| 报告修订快照 | 按现有日报扩展 |
| 幂等操作记录 | 通常新增 |

具体模型名需要检查你的代码后确定。

## 6.3 必需 MCP 工具

### 只读工具

| 工具 | 用途 |
|---|---|
| `smoke_get_review_context` | 批次、用例、特性和执行上下文 |
| `smoke_read_evidence` | 授权读取有限大小的证据片段 |
| `smoke_search_issues` | 查询本地诊断与可选外部问题 |

### Worker 控制工具

| 工具 | 用途 |
|---|---|
| `smoke_claim_review_job` | 领取任务 |
| `smoke_renew_review_lease` | 续租 |
| `smoke_fail_review_job` | 记录失败／进入重试或人工处理 |

### 业务写工具

| 工具 | 用途 |
|---|---|
| `smoke_mark_case_result` | 提交复核结论，不改写原始执行结果 |
| `smoke_create_or_link_issue` | 创建候选问题／关联已有问题及证据 |
| `smoke_finalize_review` | 原子完成当前复核的结果和问题关联 |
| `smoke_generate_report` | 生成结构化报告快照 |
| `smoke_publish_report` | 校验并发布报告 |

前三类业务需求均单独提供工具，但 Worker 的正常提交路径建议使用 `smoke_finalize_review`，将多个写入放在一个业务事务中。

这样避免：

```text
问题创建成功
    但复核结果写入失败
    导致报告中出现孤立问题
```

独立工具仍可用于受控补充或人工操作。

## 6.4 权限调用链

```text
AI Agent
    只有只读工具
         │
         ▼
返回结构化建议
         │
         ▼
Worker 校验与策略判断
         │
         ▼
受限写工具
         │
         ▼
Odoo 服务端再次校验
```

LLM 不接触写账号密钥，也不能通过“建议调用某个工具”间接绕过 Worker 的发布规则。

## 6.5 写接口公共信封

```json
{
  "schema_version": "1.0",
  "idempotency_key": "stable-operation-key",
  "run_id": "run-example-001",
  "input_revision": 1,
  "attempt_id": "attempt-example-001",
  "expected_review_revision": 0,
  "lease_generation": 1,
  "lease_token": "opaque-server-issued-token"
}
```

服务端必须验证：

- 调用方有权限操作该产品／批次。
- 当前租约有效。
- 租约代次匹配，旧 Worker 无法迟到提交。
- 输入快照仍是当前分析依据。
- 人工结果未被更新或锁定。
- 同幂等键重复请求内容一致。
- 证据引用属于授权记录。
- 状态转换合法。

幂等键不能依赖模型生成，应由程序稳定生成。

## 6.6 错误码

建议统一：

```text
VALIDATION_ERROR
ACCESS_DENIED
IDEMPOTENCY_CONFLICT
STALE_REVISION
LEASE_EXPIRED
EVIDENCE_UNAVAILABLE
INPUT_NOT_SEALED
HUMAN_RESULT_LOCKED
DEPENDENCY_UNAVAILABLE
```

只对明确可重试错误自动重试。权限错误和参数错误不能无限重试。

## 6.7 大文件访问

MCP 用来传：

- 证据元信息。
- 小片段文本。
- 按需图片或派生结果。
- 受控资源引用。

不通过一个工具返回完整几 GB 日志或录像。

设置：

```text
最大读取字节数
最大行数
单次截图数量
单次录像时间窗
单任务工具调用次数
```

# 七、结果、报告与上线规则

建议保存为：`docs/07-report-and-rollout.md`

## 7.1 有效结果

继续使用：

```text
PASS
FAIL
BLOCKED
NEEDS_REVIEW
NOT_TESTED
```

建议特性汇总优先级：

```text
FAIL > NEEDS_REVIEW > BLOCKED > NOT_TESTED > PASS
```

前提是先依据策略为每个必需 `plan_item` 选出有效结论，再进行特性汇总。

### 没有充分分析的失败

在影子模式中：

```text
原始失败：可见
AI 建议：可见
正式结果：由现有人工流程决定
```

不能因为 AI 还没完成，就将失败项从统计中排除。

## 7.2 报告结构

```text
1. 产品与构建信息
2. 输入完整性
3. 原始执行统计
4. 复核统计
5. 特性结论
6. 新发现问题
7. 已知问题复现
8. 阻塞项与待人工项
9. 优先排查与解决方向
10. 重跑建议
11. 分析局限
12. 审计与版本信息
```

### 新增重点：行动清单

| 优先级 | 影响特性 | 现象 | 建议负责人 | 建议动作 | 依据 | 验证方式 |
|---|---|---|---|---|---|---|

报告需要区分：

- 已确认事实。
- 根因假设。
- 建议动作。
- 已执行动作。

本期最后一项通常为空，不能将“建议重跑”写成“已经重跑”。

## 7.3 单产品报告与每日总览

```text
单产品报告：
    对应确定 run_id 和输入／复核快照。

每日总览：
    聚合当天预期的产品报告。
```

每日总览必须显示：

- 哪些产品已经完成。
- 哪些产品尚未开始／尚未回传。
- 哪些产品存在同日多个构建。
- 每个产品当前展示的是哪一个构建。

不能直接取“最后收到的一条”当作当天正式构建。

业务日期和时区作为配置项，不根据服务器默认时区推断。

## 7.4 上线三个阶段

### 阶段 A：影子运行

- AI 写分析建议。
- 自动生成报告草稿。
- 人工仍决定正式结论。
- 所有失败建议经过人工核对。

### 阶段 B：受限自动化

开放：

- 已批准知识的严格复用。
- 自动创建候选诊断。
- 自动关联 occurrence。
- 已批准规则范围内的正式标记。

### 阶段 C：扩大自动化

依据真实评估决定，不按“模型自报置信度大于某个值”直接开放。

最优先监控：

1. 产品缺陷被错误排除的比例。
2. 不应通过却被标记通过的比例。
3. 错误复用问题的比例。
4. 建议是否确实帮助人工缩短排查时间。

```text
1. 检查证据完整性。
2. 确认目标构建、用例目标、失败步骤和时间范围。
3. 列出直接观察到的事实。
4. 查询已知诊断。
5. 比较版本、产品、必要条件与排除条件。
6. 提出最可能原因及替代假设。
7. 给出按优先级排序的排查／修复／验证建议。
8. 按指定 Schema 输出 JSON。

结论要求：
- 每个关键判断都引用可验证的证据。
- 区分事实、推断和未知。
- ADB 断连不能单独证明环境问题。
- 没看到错误日志不能证明产品没有缺陷。
- 相同错误文本不能直接认定相同根因。
- 已知缺陷仍可能导致本次失败。
- 外部问题查询失败不等于没有问题。
- 无法区分原因时使用 UNKNOWN / NEEDS_REVIEW。
- 不伪造日志、行号、问题 ID 或修复结论。

建议要求：
- 说明检查什么、为什么检查、预期观察到什么。
- 标记是否需要设备访问和人工操作。
- 首期所有建议 execution_policy 为 ADVICE_ONLY。
- 避免只输出“检查环境”“建议重跑”等泛泛建议。
- 优先利用已存在材料，说明确实缺少的证据。

只输出符合 AnalysisResult Schema 的 JSON。
不输出隐藏思维过程；提供简洁依据、证据引用、替代假设和限制。
```

# 十、按这个顺序开发

建议保存为：`docs/08-development-backlog.md`

| 任务 | 内容 | 验收重点 |
|---|---|---|
| T00 | 现有模型及接口盘点 | 生成真实映射，不编造 |
| T01 | 完整 Schema、枚举和合成样例 | 合法／非法样例自动校验 |
| T02 | 核心规则＋Fake Agent | 环境失败不能通过 |
| T03 | Odoo 复核记录与人工确认 | 不覆盖人工结果 |
| T04 | 特性汇总＋报告草稿 | 缺失、重跑、参数化统计正确 |
| T05 | Apexive 测试库接入 | 读写隔离、真实协议互通 |
| T06 | Collector 与完成钩子 | 断网补传、异常中断、控制步骤排除 |
| T07 | Worker 领取／续租／恢复 | 重复投递和旧租约拒绝 |
| T08 | 真实模型与证据处理 | 脱敏、结构校验、有限工具循环 |
| T09 | 问题与诊断积累 | 候选不能直接自动复用 |
| T10 | 影子运行与评估 | 误判产品缺陷、错误复用、建议价值 |
| T11 | 有限自动生效 | 规则白名单、人工锁定、回滚 |
| T12 | 外部问题系统接入 | 查询失败不伪装成无结果 |

## 第一阶段必须做的回归测试

尤其优先覆盖：

1. 最后控制步骤不进入产品通过率。
2. 测试进程提前终止也能形成不完整报告。
3. 同一回调重复提交不创建重复记录。
4. 两个 Worker 不重复生效同一复核。
5. 旧 Worker 无法覆盖接管后的结果。
6. 人工已确认结果不能被 AI 覆盖。
7. 环境失败保留阻塞。
8. 已知产品缺陷仍然失败。
9. 图像未脱敏时禁止外发。
10. 日志中包含恶意指令不能引发写操作。
11. 人工重跑保留原失败历史。
12. 分析时输入变化，拒绝将旧结果应用到新快照。
13. 外部问题系统超时，不返回“无已知问题”。
14. 同一症状不同根因，不被强制合并。
15. 报告中统计与数据库快照一致。

# 十一、现在需要你提供的不是更多背景，而是三组接入材料

架构可以按上述方案推进。生产适配只需要补充下面三组材料：

### 1. Odoo 模型信息

最好提供相关模型定义；也可以仅提供：

```text
产品模型：
特性模型：
团队模型：
用例模型：
问题模型：
日报／特性每日结果模型：
这些模型之间的关联字段：
```

不需要提供整个项目，更不要提供生产数据库和密码。

### 2. 一次脱敏的测试结果目录

至少包含：

```text
一个成功用例
一个产品问题失败用例
一个环境问题或原因不明的失败用例
当前结果 JSON／文本
目录结构
对应日志片段
用例到特性的映射方式
```

不用先发送完整录像或几 GB 日志。

### 3. 制品访问方式

只需确认：

```text
目前日志保存在执行机，还是已有共享存储？
中央服务器是否能读取？
结果文件何时写完，谁负责关闭日志？
任务结束回调在哪里最方便增加？
```

**我的建议是先启动 T00—T04：用 Fake Agent 把数据、人工确认、特性状态和报告跑通，再接真实模型。**这样第一轮就能验证你最熟悉的 Odoo 业务闭环，也避免把接口问题、状态问题和模型判断问题混在一起排查。
