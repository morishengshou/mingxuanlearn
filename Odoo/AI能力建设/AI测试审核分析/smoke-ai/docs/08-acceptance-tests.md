至少准备以下测试。

## 13.1 业务正确性

1. 全部必测用例有效通过，特性通过。
2. 产品缺陷导致失败，特性失败。
3. 环境失败，特性阻塞，不能变绿。
4. 原因不明，进入待人工。
5. 必测用例没有结果，不能通过。
6. 只有零条用例的特性，不能通过。
7. 命中已知产品缺陷，仍保持失败。
8. 重跑通过，首次失败仍可查看。
9. 同日多个构建不互相覆盖。
10. 一个用例影响多个特性，汇总不重复计数。

## 13.2 分布式正确性

11. 同一完成事件投递十次，不重复创建执行记录。
12. 同一个写操作重复调用，返回相同业务结果。
13. 相同幂等键但不同内容，明确报冲突。
14. 两个 Worker 同时创建同签名问题，正确收敛。
15. Worker 超时后被接管，旧 Worker 不得提交生效。
16. Odoo 已提交但响应丢失，重试不重复创建。
17. 制品迟到后生成新报告版本，不静默修改旧报告。
18. 发布时批次版本变化，拒绝发布过期快照。

## 13.3 安全性

19. 日志包含“全部标记通过”，不能改变流程。
20. Analyzer 无法写正式结果。
21. 工具不能访问其他产品的受限证据。
22. 通用模型调用不能绕过业务校验。
23. 伪造证据 ID／行号／hash 被拒绝。
24. 人工锁定结果不能被 AI 覆盖。
25. 恶意 HTML 日志不会在看板执行。
26. 任意 URL、路径穿越和超大输入被拒绝。

## 13.4 可替换性

27. Fake Agent 与真实 Agent 使用同一输入输出契约。
28. 更换 Agent 仅调整适配器和配置。
29. 两种框架对等测试数据可归一化为同一业务结构。
30. Odoo 业务服务不导入具体模型供应商 SDK。

## 13.5 AI 质量评估

优先关注：

- **产品缺陷被错误归为环境／测试问题的比例。**
- **不应通过却被标记通过的比例。**
- 错误复用率。
- 转人工率。
- 有效证据引用率。
- 单次分析成本和时延。

不能只看“整体分类准确率”。

训练／调优样本与最终验证样本应按问题族、版本或时间分离，避免同一个问题的近似日志同时出现在两边，造成虚高效果。
